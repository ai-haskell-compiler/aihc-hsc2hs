# aihc-hsc2hs

`aihc-hsc2hs` is a drop-in replacement for [`hsc2hs`](https://hackage.haskell.org/package/hsc2hs),
the preprocessor that turns `.hsc` files into Haskell FFI bindings.

It exists to make cross-compilation work **100% of the time**. Upstream
`hsc2hs` answers questions like `#size struct stat` by compiling a small C
program and *running it on the build machine*, which is impossible when the
target is a different platform. Its `--cross-compile` mode avoids execution but
rejects whole directives (`enum`, `const_str`, custom templates) with
`cannot be handled in cross-compilation mode`, and its output differs from
native mode. Packages that build fine natively therefore break the moment you
cross-compile them.

`aihc-hsc2hs` produces the same output as upstream, in native and cross builds
alike, for any target Clang can compile for.

## How it works: never run, only inspect

The candidate **never executes code compiled from an input `.hsc` file**. There
is no emulator, WASI runtime, JIT, native probe or link-and-run fallback.
Instead, every directive becomes a compile-time constant that Clang evaluates
for the target ABI, and the answers are read straight out of the object file:

```text
.hsc source
  -> pure parser and template lowering
  -> one C probe with a fixed-size answer record per directive
  -> clang --target=TRIPLE --sysroot=DIR -c    (the only external step)
  -> ELF / Mach-O / COFF object bytes
  -> pure section decoder, answer validation
  -> pure Haskell reconstruction, byte-identical to upstream
```

Each answer is a 24-byte constant initialiser placed in a dedicated section
(`aihc_ans`, or `__aihc_ans` on Mach-O). Values are encoded as explicit byte
arrays, so decoding never depends on target endianness, pointer size or
relocations. Since only compilation happens, a Nix-provided Clang, sysroot and
the package's C dependencies are everything a target needs.

Some custom `#let` templates run arbitrary C at preprocessing time. There is no
general static equivalent for those, so compatibility grows by implementing the
template families used in practice (string extraction, bindings-DSL generators)
as explicit reconstruction rules, never by adding an execution fallback. See
[architecture](docs/architecture.md) for the details and limits.

## Stackage compatibility

The measure of success is simple: how many of the `.hsc` files in Stackage does
`aihc-hsc2hs` process with output **identical, byte for byte**, to upstream
`hsc2hs`? Every file in the snapshot is preprocessed inside its real package
build context by both tools, on the same Clang, sysroot and headers, and the
results are compared without any normalisation of whitespace, pragmas, encoding
or line endings.

Reading the table:

- **Byte-exact matches** counts files where both tools succeeded and produced
  identical Haskell and companion files. This is the number we drive to 100%.
- **Candidate failures** are files `aihc-hsc2hs` rejects, mostly unsupported
  directives such as `#enum`, `#const_str` and custom templates.
- **Divergences** are files where both tools succeeded but the bytes differ.
- **Upstream cross failures** are files upstream's own `--cross-compile` mode
  cannot handle. They are counted as candidate failures too, so a candidate
  success there would still be unverified.
- **Inapplicable** files are not selected by any buildable Cabal component for
  that target (for example Windows-only modules). They are accounted for
  explicitly, never dropped.

These numbers come from the reviewed baselines in `data/baselines/`, which
`nix flake check` asserts exactly on every commit: any improvement or
regression fails CI until the baseline is updated. The
[Stackage statistics](.github/workflows/stackage-stats.yml) workflow re-measures
the corpus every week and opens a pull request when the numbers change, so this
section stays current without ever accepting a new baseline silently.
[Corpus contexts](docs/corpus-contexts.md) documents the snapshot, the build
contexts and how to reproduce a measurement.

## Usage

```sh
nix build .#aihc-hsc2hs
result/bin/aihc-hsc2hs --help
result/bin/aihc-hsc2hs --target aarch64-unknown-linux-gnu --sysroot "$SYSROOT" \
  --cc clang -I include -o Bindings.hs Bindings.hsc
```

The CLI accepts the common `hsc2hs` options (`-o`, `-I`, `-D`, `-i`, `--cc`,
`--cflag`, `--cross-compile`) plus two required, explicit target settings:
`--target TRIPLE` and `--sysroot DIR`. Nothing about the target is inferred
from the host. `--cross-compile` selects upstream's cross-mode macro handling
and output pragmas; both modes only ever compile.

The Cabal package (Unlicense) exposes the `Hsc2hs` and `Hsc2hs.Object`
libraries. `generate` and `generateBytes` drive Clang with a configurable
timeout; the pure `prepare`, `decodeAnswers` and `finish` functions let callers
plug in their own compiler service.

## Development

```sh
nix develop                      # Clang, LLVM, GHC, Cabal, upstream hsc2hs, Python
nix flake check -L               # unit tests, fixtures, harness, corpus baselines
nix build .#stackage-hsc         # the pinned Stackage .hsc inventory
nix build .#stackage-native-report   # fresh measurement (ARM64 Linux/macOS)
nix build .#stackage-cross-report    # fresh cross measurement (ARM64 macOS)
```

To update the compatibility numbers after a change, build the report, review
its diagnostics, then import it and regenerate this README:

```sh
python3 tools/readme-stats.py --import result/report/summary.json --write
```

Rename `summary.json` to `<system>-<mode>.json` (for example
`aarch64-linux-native.json`) before importing so it lands on the right
baseline. `nix flake check` fails if this README disagrees with the baselines
or the test fixtures. Baselines are exact: setup failures, native-oracle
failures, timeouts and crashes are never accepted.

Further reading: [testing and the comparison harness](docs/testing.md),
[corpus contexts and measurement](docs/corpus-contexts.md),
[architecture](docs/architecture.md).
